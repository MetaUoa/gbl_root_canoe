## XBL comparison

Both images report:

`BOOT.MXF.2.5.1-00265-PAKALA-1.104700.25`

and:

`IMAGE_VARIANT_STRING=SocPakalaLAA`.

The two `xbl.img` files differ at only **200 bytes (~0.0168%)**, grouped into six small runs. The changed regions look like metadata / authentication material rather than a broad executable rewrite. This is useful evidence that the XBL main code lineage is stable across these two builds, but it is **not** a flashing-compatibility guarantee.

`xbl_config.img` changes much more substantially: about **30.3%** of bytes differ.

## LinuxLoader comparison

The old loader is one 4 KiB page larger:

- 16.0.3.501: `.text = 0x9C000`, total `0xC4000`
- 16.0.10.501: `.text = 0x9B000`, total `0xC3000`

The overall binaries are not byte-layout compatible, so fixed offsets must remain per-build profiles.

Both loaders contain:

- `androidboot.vbmeta.device_state`
- `unlocked`
- `locked`
- `androidboot.verifiedbootstate=`
- `orange`
- `green`
- OPlus unlocked warning strings
- `KeyMasterSetRotAndBootState`

Both loaders lack ASCII and UTF-16 `efisp`.

## 16.0.3.501 fake-lock offsets

Device-state block:

- unlock ADRP: `0x4C38C`
- unlock ADD: `0x4C390`
- lock ADRP: `0x4C394`
- lock ADD: `0x4C398`
- key ADRP/ADD: `0x4C39C / 0x4C3A0`
- CMP/CSEL: `0x4C3A8 / 0x4C3AC`

Verified-state table:

- table: `0xA3CB0`
- green pointer: `0xA3CB8 -> 0x87995`
- orange pointer: `0xA3CC8 -> 0x84822`

The offline patch retargets the unlock string pair to the existing locked string and redirects the orange table entry to green. The real Qualcomm DeviceInfo unlock bit and KeyMaster/TEE path are untouched.

## Old-only verified-boot strings

The 16.0.3.501 loader contains these strings that are absent from 16.0.10.501:

- `LoadImageNoAuthWrapper`
- `LoadBootImageNoAuth`
- `LoadImageAndAuthVB1`

Public Qualcomm-derived EDK2 sources show `LoadImageNoAuthWrapper` is selected for `NO_AVB` and calls the generic `LoadImageNoAuth` path. Therefore these symbols are recorded as a **verified-boot implementation delta**, not as sufficient proof of a GBL exploit path.

## GBL / EFISP conclusion

The early ARB1 sample does **not** restore the legacy `efisp` marker. Related GBL research also documents builds where this marker is absent, so marker absence alone does not describe every staged-development path; however, it does mean this sample cannot yet be accepted as a known vulnerable persistent loader for the current installer model.

Status:

- software-visible fake-lock: **offline validated**
- exact 16.0.3.501 profile: **implemented**
- exact 16.0.10.501 profile: **implemented**
- persistent GBL/EFISP loader on PJZ110: **not validated**
- device flashing: **disabled**
