# OnePlus 13 PJZ110 / SM8750 adaptation

This branch adds **version-scoped, fail-closed** research profiles for the China OnePlus 13 (`PJZ110`) on SM8750/Pakala. Offline profiles currently cover `PJZ110_15.0.0.702(CN01)`, `PJZ110_16.0.3.501(CN01)`, and `PJZ110_16.0.10.501(CN01)`.

## Current status

| Area | Status |
| --- | --- |
| Extract `LinuxLoader.efi` from profiled `abl.img` | Working |
| Detect exact PJZ110 profiles | Working for 15.0.0.702, 16.0.3.501, and 16.0.10.501 |
| `androidboot.vbmeta.device_state` software-visible fake-lock patch | Working offline |
| Verified-boot state table `orange -> green` patch | Working offline |
| Binary diff allowlist / manifest | Working |
| Qualcomm DeviceInfo / `is_unlocked` | Intentionally untouched |
| KeyMaster / TEE RootOfTrust | Intentionally untouched |
| OPlus unlock-warning suppression | Research |
| GBL / EFISP persistent loader | Not validated; legacy `efisp` marker is absent across all three sampled ColorOS 15/16 profiles |
| Automatic ABL downgrade | Disabled for this adaptation |
| Device flashing | Not enabled |

The current implementation is therefore an **offline patcher**, not a flash-ready release.

## Offline analysis

```bash
python3 tools/pjz110_patch.py analyze abl.img
python3 tools/pjz110_patch.py analyze abl.img --json
python3 tools/pjz110_patch.py analyze abl.img --extract LinuxLoader.efi
```

Unknown or changed firmware can be analyzed, but it is not writable.

## Offline patch

```bash
python3 tools/pjz110_patch.py patch abl.img patched.efi
```

A JSON manifest is written next to the output. The exact known profile changes only two guarded regions:

1. At `0x4AF3C/0x4AF40`, the `unlocked` ADRP/ADD pair is retargeted to the existing `locked` string. The following `CSEL` remains intact; both branches therefore resolve to `locked`.
2. At `0xA2CA8`, verified-state enum `1` (orange) is redirected to the existing `green` string.

For the profiled image, the resulting output SHA256 is currently:

`34dbedd47b33acf4c131b5db927a5ef7cf9be214facbe6f98fe044dc448b61f0`

The tool validates the source SHA256, exact instruction words, exact state-table values, image size, and an allowlist of changed byte offsets before producing output.

## What this does not do

This branch does **not** write Qualcomm `DeviceInfo.is_unlocked`, and does not modify the `VBRwDeviceState`, KeyMaster, or TEE RootOfTrust path. It also does not claim that software-visible state is equivalent to a physically locked bootloader or hardware attestation state.

## GBL / EFISP blocker

Upstream legacy code looks for UTF-16 `efisp` inside LinuxLoader. The profiled PJZ110 LinuxLoader contains neither ASCII nor UTF-16 `efisp`, so the old SM8845/SM8850 GBL patch is not applicable.

Until the PJZ110 GBL/EFI loading path is identified and validated, this branch must remain fail-closed for installation/flashing.

## Current deployment boundary after R4

The early-ARB1 and ColorOS 15 comparison work is complete. Subsequent exact
Retail analysis also closed the stock temporary execution candidates through
R4-A→R4-D:

~~~text
R4-A stock RAM/FV/EFI mechanisms          PASS-ENUMERATED
R4-B mechanisms usable before LinuxLoader INTERNAL-ONLY
R4-C external controllable pre-LL source  NONE-FOUND
R4-D stock non-flashing EFI carrier       CLOSED
~~~

The exact current UFS path stages the ABL FV through the Retail-allowed PIL
configuration from a fixed raw partition source. The platform also contains
authenticated PIL buffer loading, a flashless preloaded-RAM ABL mechanism, and
a debug `FV_Region` ToolsFV RAM mechanism, but none is a proven external,
temporary, pre-LinuxLoader carrier on the current Retail/UFS device.

Fastboot is implemented by the already-running LinuxLoader. Its download RAM is
therefore post-LinuxLoader, and the stock `boot` command consumes Android boot
images through `LoadImageAndAuth -> BootLinux`, not arbitrary UEFI PE images.

The project remains fail-closed for deployment. No live EFI execution or
boot-chain write is currently requested.

Detailed R4 report:
[`PJZ110_R4_STAGED_MEMORY_EFI_RE.md`](PJZ110_R4_STAGED_MEMORY_EFI_RE.md).

## Next research target

Any further deployment work is a separate design milestone rather than another
stock-route reachability test. Before a persistent experiment is considered, it
must define an explicit reversible/A-B rollback contract and continue to leave
DeviceInfo, VBRwDeviceState, RPMB, KeyMaster and TEE state untouched.

## Early ARB1 comparison

The supplied `PJZ110_16.0.3.501(CN01)` sample has now been analyzed and added as a second exact offline profile. Its `LinuxLoader.efi` is `0xC4000` bytes with SHA256 `1873bdfd2654decba1ac50d2c0d1d3aa61423f11123f7301743be78da7f63333`.

Its patched output SHA256 is `ef6025146ba868832d704d4a62efc2cf4387e965e57f1ad7426b8186cfb57ce4`, with seven changed bytes. The detailed comparison is in [`PJZ110_1603501_DIFF.md`](PJZ110_1603501_DIFF.md).

The old loader retains `LoadImageNoAuthWrapper`, `LoadBootImageNoAuth`, and `LoadImageAndAuthVB1`, which are absent from 16.0.10.501. Public Qualcomm-derived EDK2 source shows these belong to older verified-boot code paths; they are useful RE anchors but are not treated as proof of a usable persistent GBL loader.

- changed byte count: **7**
- XBL version: `BOOT.MXF.2.5.1-00040.1-PAKALA-1.81269.25`

The launch-era ColorOS 15 sample still lacks both ASCII and UTF-16 `efisp`. This crosses a genuine XBL generation boundary relative to the ColorOS 16 `00265` baseline without revealing the original project's legacy direct-EFISP loader marker.

Detailed comparison: [`PJZ110_THREE_GEN_DIFF.md`](PJZ110_THREE_GEN_DIFF.md).

This strengthens the conclusion that PJZ110 deployment should not be designed around blindly porting the legacy SM8845/SM8850 `efisp` string patch. The project remains offline-only until an alternative PJZ110 chainload path is validated.
